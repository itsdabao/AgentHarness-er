## Yêu cầu và nguồn đối chiếu

Người dùng yêu cầu tạo phase interface riêng, xem có thể đặt trước Phase 4 và 5
không, với scope rõ theo assessment và code hiện có. Trong lượt này đã đọc nội dung
file `docs/requirements/assessment.docx`.

Assessment yêu cầu điều khiển qua RPC, session/task/status, loop nhiều bước, MCP,
trace bền vững, resume và demo cancel giữa chừng cùng failure handling. Đề không
bắt buộc web UI. Terminal client là cách trình bày thêm cho demo; demo bằng lệnh
hoặc script của Phase 4 vẫn phải hoạt động độc lập.

## Quyết định về thứ tự

Đặt Phase 4.5 sau Phase 4, trước bonus Phase 5. Interface hoàn chỉnh dùng RPC của
Phase 4 nên chưa thể nghiệm thu trước dependency đó. Có thể thiết kế command hoặc
renderer trước, nhưng không tạo một client gọi thẳng AgentService rồi đổi lại sau.
Giữ nguyên số phase và acceptance ID cũ. Phase 5 có recommended_after cho 4.5,
không biến interface optional thành dependency bắt buộc.

## Scope đã đưa vào kế hoạch

- Terminal có command prompt và event feed; nhập cancel được trong lúc đang watch.
- Tạo/chọn session bằng ID, gửi task, xem/watch/cancel run, đọc event theo cursor.
- Hiện trạng thái do server xác nhận, tool arguments/results/errors và final output.
- Có chế độ JSON; tái sử dụng public RPC/event contract, kiểm soát payload dài và
  escape terminal control sequences trong dữ liệu tool.
- Reattach sau disconnect/restart; follow-up tạo run mới trong session cũ.
- Không tự gửi lại task khi mất response. Cancel request chưa được xác nhận không
  được hiển thị thành cancelled; completion thắng race thì hiển thị completed.
- Stop watch chỉ dừng quan sát. Quit/EOF phụ thuộc lifecycle của transport Phase 4;
  phải mô tả rõ thay vì hứa server luôn tiếp tục chạy.
- Hiện model-step progress, không yêu cầu private chain-of-thought hoặc tự dựng suy nghĩ.

Không thêm session/run search APIs, provider switch/fallback, truy cập SQLite/MCP
trực tiếp từ client hay web frontend. Dùng lại fixture Phase 4 để test qua RPC thật.
